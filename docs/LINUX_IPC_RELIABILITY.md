# Надёжная передача команд в Linux

## Зачем это нужно

В Linux ярлык `clickntranslate --ocr` запускает ещё один процесс, который
передаёт команду уже открытому приложению через локальный UNIX-сокет.
Если приём команд ждёт выполнения предыдущего обработчика, серия нажатий
может переполнить очередь подключений. Ошибка соединения при этом ещё не
означает, что основное приложение завершилось.

Эта доработка касается команд и повторного запуска в Linux. Она не меняет
распознавание, перевод, интерфейс или механизм единственного экземпляра Windows.

## Что реализовано

1. **Приём отделён от обработки.** Один поток принимает короткие команды,
   второй передаёт их обработчику по очереди. Медленный обработчик больше не
   останавливает сам приём подключений.
2. **Очередь ограничена.** До 128 команд могут ожидать обработки, ещё одна
   может находиться внутри обработчика. При заполнении сервер отвечает `busy`,
   не добавляя команду в очередь.
3. **Команды ждут готовности окна.** `main.py` создаёт сервер с
   `start_ready=False`, затем вызывает `set_ready()` после установки
   `_main_window_ref`. Команда не теряется только потому, что окно ещё создаётся.
4. **Медленный отправитель не блокирует остальных.** Неблокирующий приём через
   `selectors` обслуживает до 128 незавершённых подключений. На получение
   команды отводится 5 секунд, размер кадра ограничен 64 байтами.
5. **Право на сокет закреплено блокировкой.** Перед проверкой и созданием
   сокета процесс захватывает `flock` на файле `clickntranslate.sock.lock`.
   Блокировка удерживается до завершения обработчика и очистки канала.
6. **Чужой действующий сокет не удаляется из-за таймаута.** Удаление оставшегося
   сокета разрешено только после `ECONNREFUSED`, проверки владельца и совпадения
   устройства/inode. Обычные файлы и символические ссылки не подменяются.
   Экземпляр, которому не удалось привязать сокет, не удаляет сокет победителя.
7. **Неуспех виден вызывающему процессу.** Перегрузка и неподтверждённая передача
   заканчиваются сообщением в stderr и кодом выхода `75`, а не ложным успехом.

Backlog установлен в 128: это запрошенный размер очереди ядра, а не обещание
принимать любую нагрузку. Его фактическое поведение зависит от Linux.

## Значение ответов

| Статус клиента | Значение | Поведение второго запуска |
| --- | --- | --- |
| `ACCEPTED` / `ok` | Команда помещена в очередь в памяти | Выход с кодом 0 |
| `BUSY` / `busy` | Нет места в очереди команд или подключений | Выход с кодом 75 |
| `UNAVAILABLE` | `connect` вернул ENOENT или ECONNREFUSED до отправки | Попытка захватить блокировку и стать основным экземпляром |
| `FAILED` | Передача не подтверждена: таймаут, доступ, обрыв или иной ответ | Выход с кодом 75, без автоматического повтора |

Если блокировку успел захватить другой запуск, разрешена одна попытка передать
ему команду: до этого клиент получил `UNAVAILABLE` и ничего не отправлял.
После потери ответа повтор не выполняется: команда могла уже попасть в очередь.
Старый `send_command()` сохранён для совместимости; он возвращает `True` только
для `ACCEPTED`. Его `False` **нельзя** интерпретировать как отсутствие приложения.

## Для разработчика

- Основная реализация: `single_instance.py`; подключение к окну: `main.py`.
- Обработчик вызывается вне потока Qt. Он должен быстро передать работу через
  сигнал Qt, как уже делает `handle_shortcut_command`, а не менять виджеты напрямую.
- FIFO означает порядок добавления полных команд в очередь. Это не обязательно
  порядок запуска клиентских процессов или начала их подключения.
- `stop()` прекращает приём; `join()` позволяет дождаться завершения потока.
  Готовый обработчик разбирает принятую очередь перед освобождением блокировки.
  Если окно так и не стало готово, оставшиеся команды отменяются с записью в лог.
- Приложение при выходе ждёт канал не более 2 секунд. При зависшем обработчике,
  аварии процесса или уже остановленном цикле Qt выполнение действий не гарантируется.
- Блокировка освобождается ОС при смерти процесса. Файл `.lock` намеренно
  остаётся на диске. **Не удаляйте его для устранения ошибки запуска**: два
  процесса могут заблокировать разные inode одного и того же имени.
- Для перехода со старой версии сначала полностью закройте её. Старые сборки
  не соблюдают новую файловую блокировку. Это координация экземпляров приложения,
  а не защита от злоумышленника с тем же UID.

## Как проверить

Из корня репозитория в Linux, без OCR-моделей, сети и платных API:

```bash
python3 -m unittest discover -s tests -p 'test_single_instance*.py' -v
```

Проверки используют временный каталог, не сокет открытого приложения. В наборе:
обычная доставка всех команд; фрагментированные сообщения; 128 отправителей до
готовности окна; заполненная очередь; медленный обработчик; лимит подключений;
таймаут неполного сообщения; некорректные команды; исключение обработчика;
одновременный старт двух процессов; гибель владельца; восстановление сокета;
защита от удаления действующего или подменённого пути; поведение `main.py`
при перегрузке, старте и завершении.

В Windows тот же набор выполняет проверки протокола и логики старта без реального
Linux-сервера; платформозависимые проверки пропускаются. Для настоящего UNIX-сокета
можно использовать Linux-контейнер с репозиторием только для чтения:

```powershell
docker run --rm --network none `
  --mount "type=bind,source=$($PWD.Path),target=/app,readonly" `
  --workdir /app --env PYTHONDONTWRITEBYTECODE=1 `
  python:3.12-slim python -m unittest discover -s tests -p 'test_single_instance*.py' -v
```

Общий регрессионный набор, если установлены зависимости проекта:

```powershell
$env:QT_QPA_PLATFORM = 'offscreen'
& .\.venv\Scripts\python.exe -m pytest -q
```

Перед выпуском Linux-сборки отдельно нужен ручной тест на реальном рабочем столе:
повторный запуск, открытие окна и OCR через назначенную команду, запуск команды
во время загрузки окна и нормальное завершение. Контейнерные тесты не проверяют
порталы Wayland, экранный захват и готовую AppImage.

## Что нельзя обещать по этим тестам

`ok` подтверждает постановку в память, **не завершённое OCR-действие**.
Очередь не сохраняется после аварии, протокол не содержит идентификаторов для
защиты от повторов. Ограничение очереди IPC не ограничивает очередь событий Qt.
Показатель исторического прототипа из статьи не переносится автоматически на
этот новый код: локальные регрессионные проверки не являются новым научным
экспериментом или гарантией 100% доставки в любых условиях.
