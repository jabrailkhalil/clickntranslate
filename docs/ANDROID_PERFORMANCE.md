# Android: ограничения нагрузки и реальные измерения

Цель — быстрый вход в перевод и ограниченное потребление памяти. Количество исходных файлов и размер APK сами по себе этого не доказывают.

## Проверенная точка Wave4

- Оптимизированный ARM64 QA4:51145474байта (48.78MiB), включая пять поддерживаемых ML Kit OCR scripts и независимые native engines. Новая адаптивная навигация не добавила библиотек, сети или background workers.
- Финальный десятиминутный API26 x86 capture:103 цикла, maxPss185903KiB (181.55MiB),608.333с. После Stop освобождены worker и owned overlay-окна. [Журнал и границы](qa/wave4/README.md).
- Одно ручное cold-start наблюдение QA4 на API36 через ARM native bridge: [`am start -W`](qa/wave4/manual/final-qa-cold-start.txt) TotalTime632ms/WaitTime638ms. Это первое отображение окна, не время полной готовности и не статистический benchmark. По одному измерению ускорение не заявляется.

Эмуляторные измерения не подтверждают расход батареи, нагрев, многочасовую работу, low-memory поведение всех устройств или физический ARM64. PSS не является размером Java heap. Сравнение разных ABI и native bridge не заменяет сравнение на одном телефоне.

## Границы реализации

- Один модуль, ручной application graph, существующие Compose/Material3 компоненты. Библиотеки из демонстрационных UI-шаблонов не подключались.
- Экранные кадры обрабатываются последовательно через conflated очередь. Одинаковые кадры пропускаются, контент должен стабилизироваться; bitmap освобождается при вытеснении/отмене. OCR и сетевые запросы работают вне UI-потока.
- Один лениво создаваемый ML Kit translator обслуживает абзацы одного документа и закрывается после завершения/отмены. Между независимыми документами незакрытый клиент не накапливается.
- Preview фотографий декодируется до1200px, рабочий OCR до2400px. Детализация при увеличении использует раздельные пороги1.75/1.25. Отмена освобождает ещё не опубликованные изображения; показанные Compose bitmap не recycle-ятся во время возможного чтения render thread.
- История и словари читаются страницами. Поиск изменений для capture использует SQL EXISTS вместо загрузки полного корпуса правил. Ключевые операции выполняются по индексам.

## Проверенная точка Wave5

- Оптимизированный ARM64 QA5:51244682байта (48.87MiB). Новых UI-template библиотек не добавлено. [APK audit](qa/wave5/qa-audit.json).
- Финальный десятиминутный API26 x86 capture:101цикл, maxPss188667KiB (184.25MiB),603.868с. После Stop освобождены worker и owned overlay-окна. [Журнал](qa/wave5/android26-soak.txt), [метрики](qa/wave5/android26-soak-metrics.txt).
- Одно наблюдение cold start финального QA5 на API36 через ARM native bridge:TotalTime2491мс/WaitTime2494мс. [Исходный вывод](qa/wave5/manual/final-arm64-candidate12/cold-start.txt). Отдельный чистый C7/x86 запуск показал595мс до окна/788мс FullyDrawn; это другой APK/ABI и другое состояние эмулятора. Ускорение или регрессия по этим разовым несопоставимым наблюдениям не заявляются.

Новые сохраняемые фото-задания ограничивают количество заданий, суммарный размер owned файлов, размер одного изображения и сериализованного результата. Сохранение задания не означает автоматическое разрешение сетевого повторения после перезапуска. Открытие хранилища восстанавливает метаданные; Resume/Retry запускаются явно.

BLOCKS использует геометрию уже распознанного документа. Проверка устаревания блоков не должна повторять OCR/MT в ручном режиме. Accessibility editing не должен читать поля в фоновом обработчике событий без активного явного запроса.

`AppShell` использует `ReportDrawnWhen { ready }`, чтобы [системная метрика готовности](https://developer.android.com/topic/performance/issues/launch-time) включала чтение настроек и первичный usable shell. Этот сигнал не утверждает, что отдельный пользовательский перевод, список истории или загрузка моделей уже завершены. Для сравнения скорости нужны серии на одном физическом устройстве и одинаковых данных; приведённые разовые наблюдения этого не заменяют.
